# User need database

The structured need database required by section 17 of the research mandate. 150 needs
harvested from eleven AV professions, each carrying its own source, frequency grade and time
cost, and each scored for priority.

Source dossiers: `../roles/*.md`. Grading rubric: `../METHOD.md`.

## How priority was computed

Section 26 asks for a multi-factor priority model. Two of its factors — frequency and time
saving — are recorded per need by the researchers and can be scored mechanically:

```
score = frequency(widespread 3 | recurring 2 | isolated 1)
      x time cost(hours-per-show 3 | days-per-project 3 | minutes 2 | unknown 1)

P1 = 9      P2 = 6..8      P3 = 4..5      P4 < 4
```

`hours-per-show` and `days-per-project` are weighted equally on purpose: an hour lost every show
outweighs a day lost once per project for any company doing more than a handful of shows a year.

The remaining section 26 factors — user value, error reduction, AV relevance, integration value
and complexity — are judgements rather than measurements. They are applied in
`FEATURE-STRATEGY.md`, not silently folded into this score, so that the mechanical part stays
auditable and the editorial part stays visible.

Distribution: **38 P1, 58 P2, 20 P3, 34 P4.**

## The finding that dominates the database

Eight of the eleven professions independently named the same top need, in their own vocabulary:

| Role | How they said it |
| --- | --- |
| Camera operator | "One camera position identity that flows into every downstream system instead of being retyped" — 11 hand-typed copies |
| Video engineer | "Stop typing camera identity into six to eight systems" |
| Technical director | "One source identity that propagates its name everywhere" — 5 to 7 separate UIs |
| Audio engineer | "One channel list that projects into every audience view" |
| Lighting tech | "One rig data model rendered as the many paperwork documents, not many documents maintained in parallel" |
| Network engineer | "The network plan must be derived from the same device records as the signal/cable plan" |
| Streaming engineer | "Export the delivery configuration into the formats downstream tools consume instead of making people retype it" |
| Event manager | "Render the same schedule into every audience's format from one source" |

This is not eight needs. It is one need, observed eight times from eight angles, and it is exactly
sections 22 and 23 of the mandate — enter once, single source of truth — arrived at empirically
rather than assumed. It is the highest-confidence result in the entire corpus.

## Need clusters

The 150 needs collapse into six clusters. Building against clusters rather than individual rows
is what section 19 means by synthesise rather than copy.

### Cluster A — One identity, many projections (dominant)

Every real-world thing gets exactly one record. Every label, sheet, export and device
configuration is a *rendering* of that record, never a second copy of the truth. Covers the eight
rows above plus tally/UMD mapping, ISO record naming, multiviewer layout, console scenes,
switcher mnemonics, router labels, stage plots, pack lists and tech riders.

**Why it is first:** it is the only cluster every other cluster depends on. A change-impact view
(B) is impossible without one identity to trace; a return path (C) has nothing to reconcile
against; derived logistics (F) has nothing to derive from.

### Cluster B — Change propagation: "what does this invalidate?"

A late change is the most expensive event in a production. The camera-operator dossier makes the
mechanism concrete: move a camera position and the cable call is silently invalidated — and one
wrong SMPTE run kills video, return, comms, tally and power at once. Production managers asked for
a "what does this change invalidate" view keyed to a late change; event managers asked that a
schedule change list what it invalidates. Nobody in the market offers this: the show-control
dossier records that no product answers "if I remove this connection, which 34 buttons go dead?"

### Cluster C — The return path: reality back into the plan

Plans flow outward and never come back. The lighting dossier calls this "the differentiator, not
the plot" and notes the MVR authors declared it out of scope, leaving ETC's own return path as a
spare-time community library. Network engineers want plan-versus-found reconciliation; warehouse
staff want the printed pull sheet scannable back in; production managers want a bidirectional diff
against the rental ERP rather than one-way export; technical directors want an explicit
"as planned" versus "as built" distinction.

### Cluster D — Offline, printed, and honest about staleness

Paper is not legacy behaviour to be designed away. The camera-operator research is explicit that
paper is kept deliberately, because it survives without battery and cannot silently change under
you — but that the printout goes stale with no way to tell. The need is therefore not "replace
paper" but "version-stamp the paper and give it a fast return path". Combined with the market
finding that offline is always built for the wrong half, this cluster is a genuine differentiator.

### Cluster E — Import and export fidelity

The single most damaging integration failure named across roles is **silent data loss**:
production managers report that the columns the production office added are exactly the ones that
vanish on round-trip; technical directors want sync that never destroys human-filled columns;
lighting techs want exchange files that survive a rename, a stray character or a capitalisation
change. The design rule that follows is strict: an import that cannot preserve a field must
refuse and say so, never silently drop it.

### Cluster F — The technical plan feeds logistics and commerce

Production managers want the technical plan to produce the commercial bill of materials instead of
retyping it from the quote; warehouse staff want the plan-to-pick-list gap closed; camera
operators want cable run length, path and patch derived from the camera position, and the kit list
to generate the rental order. The rental-ERP dossier confirms this is unclaimed: "nothing derives a
cable/consumable bill of materials from a plan... the single largest unclaimed piece of value
adjacent to the segment."

## Caveats on this database

- **Complaint bias applies.** These are needs voiced by people motivated to voice them. Absence
  of a need here is not evidence that it is met.
- **Time cost is self-reported and coarse.** `hours-per-show` is the researcher's grading of what
  practitioners described, not a measurement. Treat the P1/P2 boundary as a prompt for judgement,
  not a verdict.
- **29 of 150 needs carry `timeCost: unknown`** and are scored conservatively as a result. Some
  are probably P1s wearing a P3 label; they are flagged rather than inflated.
- **The seven `isolated` needs are retained deliberately.** They are recorded so they are not
  rediscovered later as if new, not because they justify building anything.
