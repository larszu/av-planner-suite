The section 16 analysis, aggregated across all sixteen market segments: 224 recorded user pain
points, each graded and sourced. Per-product detail lives in `../pain-points/*.md`.

That `integration` and `data-model` together account for 76 of 224 — a third of everything users
complain about — is itself a finding. The market's problem is not that products lack features. It
is that they cannot describe themselves to each other.

## The two findings the pain research added

The landscape pass produced the design-time thesis. The pain pass, run separately, produced two
things the landscape pass could not see, because they are only visible from the user's side.

### New finding 1: control is open-loop, and the surface lies

Five segments, independently, asked for the same thing — **read the device's real state, do not
just command it**:

| Segment | The complaint |
| --- | --- |
| Camera control | Open-loop control silently drifts; the panel shows its last command, not the camera |
| Intercom | A talk button that lies about whether the mic is actually open |
| Media playback | Wants variable values, SMPTE mode, fade status and layer transport read back, not just fired at |
| Show control | Wants control layers to report state back — "a bidirectional state mirror the rest of the system can read" |
| Lighting | Wants to read plan and patch from the console without a live console, an unofficial library, or a human |

This is the operational twin of the design-time gap. Not only does nobody hold the plan — the
runtimes cannot reliably tell you what they are currently doing. A surface that displays its own
last command as though it were device state is a lie with show-stopping consequences, and it is
the normal condition of this industry.

**It is also directly actionable for us, because we have already solved it once.** The
`video-engineer-shader` role dossier independently demanded "never display a value the system has
not confirmed", and `sony-camera-bridge` already implements the discipline: `CameraCapabilities`
gates the UI per backend so unsupported functions are disabled rather than silently failing. That
is the pattern to generalise across every module.

### New finding 2: nobody publishes machine-readable capability truth

Five segments asked for a compatibility registry that does not exist anywhere:

| Segment | What they want to know before show day |
| --- | --- |
| Camera control | Per-model control-capability matrix, so the UI only offers commands the camera can execute |
| Media playback | "A single trustworthy list of what each media server's API genuinely cannot do" |
| Tally | Which lamps will actually talk to their switcher, and warning when a vendor changes protocol |
| Audio | Which vendor devices actually interoperate, as opposed to claiming standards compliance |
| Video switching | Which firmware and control-software version combinations actually work together |

The camera-control landscape dossier found that the best dataset in that entire segment is a CSV
with French headers inside a documentation repository. Everyone rebuilds this knowledge privately
and it is stale the moment a vendor ships firmware.

This is a strong candidate for something the suite could publish as a public good — a versioned,
machine-readable registry of `device model → protocol → transport → capabilities → required
gateway → known quirks`. It is cheap relative to its value, it compounds, and it is the kind of
asset that makes a tool the default reference.

## Patterns that confirm the existing roadmap

Two roadmap items were derived from role research and are now independently confirmed from the
competitor side — different researchers, different sources, same conclusion:

- **Roadmap 2 (tally map).** The tally segment's widespread ask is verbatim: *"one authoritative,
  validated, exportable camera-to-input-to-tally-address-to-lamp map."*
- **Roadmap 3 (BOM from the plan).** The rental segment's widespread ask is verbatim: *"the
  equipment list and the technical plan (signal flow, cable schedule, rack elevation) to be one
  artefact instead of re-keyed between two tool categories."*

## The data-model complaints are a specification

The 34 `data-model` pains are unusually precise, and read as a requirements list for the identity
spine. The recurring demands:

- **Direction, connector gender and signal type as first-class properties** — because the same
  connector (XLR, BNC, RJ45) carries different things in different directions (technical planning).
- **Ports modelled as SDI/MADI/AES/genlock with direction and bitrate**, not as generic coax
  holes; a broadcast switcher must not degrade to "88 identical coax holes" (networking).
- **A signal path that survives the patch panel** — device to panel port to patch lead to
  destination as one logical connection (technical planning).
- **Stable identity for cues and device roles**, so a rehearsal-day edit does not silently
  re-point every controller button, and a main+backup pair is one configuration rather than two
  (playback, video switching).
- **A case as one scannable object whose contents and weight follow it, including nested cases**
  (asset tracking).
- **Kits where a component can be substituted without sterilising the whole kit's availability**
  (asset tracking).

`cable-planner` already satisfies several of these — `Port` with direction, `ConnectorType`,
`SignalStandard`, `StorageNode` with nested containers on the LPN principle. The gaps worth
noting are cue/role identity and kit-level partial availability.

## Where the market's pain is not our opportunity

Honesty requirement from `METHOD.md`. Several widespread complaints are real and should *not*
drive our roadmap:

- **Support quality, onboarding cost, and pricing transparency** (16 pains). These are commercial
  and organisational failings of vendors, not product gaps we can out-engineer.
- **"Voted-for feature requests never ship"** (rental). A governance complaint. Being open source
  addresses it structurally, but it is not a feature.
- **Mobile app quality** (5 pains, plus large gaps marked UNKNOWN). Real, but our mobile story is
  a LAN view; competing on native mobile apps is a different product.
- **Vendor acquisition and sunsetting** (broadcast production management). We cannot fix it; MIT
  licensing and local files are the honest answer, and they already exist.

## Caveat that bounds all of the above

Per `../METHOD.md`: Reddit, G2, Capterra and Trustpilot — the sources section 15 names for exactly
this work — were unreachable in this environment. These 224 findings rest overwhelmingly on
**GitHub issues and discussions**, which are genuine primary evidence (a long-open issue with many
reactions is strong), plus search-engine summaries of forum threads.

The systematic bias this introduces is worth naming: GitHub over-represents **open-source and
developer-adjacent products** and under-represents closed commercial products whose users never
file public issues. Riedel and Sony users do not open GitHub issues; Companion and Tally Arbiter
users do. So the pain data is thinnest exactly where the market is most expensive and most
proprietary, and every conclusion drawn from silence in those segments is weak.
